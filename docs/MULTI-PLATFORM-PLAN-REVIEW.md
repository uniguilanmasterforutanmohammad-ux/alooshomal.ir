# تحلیل راهبردی: پلتفرم استخدام، هویت مرکزی (SSO) و استک ابزارهای مشترک

این سند، **تحلیل و نظر کارشناسی** دربارهٔ نقشهٔ سه‌بخشی زیر است: (۱) پلتفرم استخدام
(Job)، (۲) سرویس هویت مرکزی (SSO)، و (۳) سرور ابزارهای مشترک. هدف این است که مشخص
شود آیا طرح زیرساختی فعلی برای این نقشه کافی و منطقی است یا نه، و کجاها ریسک دارد.

> **منبع قوانین پروژه:** `AGENTS.md` (ریشهٔ مخزن). این سند مکمل `History-Agent.md` و
> `docs/DEPLOY.md` / `docs/REVENUE-MODELS.md` است. این یک سند **تحلیلی/راهبردی** است،
> نه راهنمای پیاده‌سازی؛ هیچ‌کدام از این توصیه‌ها هنوز اجرا نشده‌اند.

> **منابع ورودی:** اسناد `job1.pdf`، `job2.pdf` (PRD و فهرست مشاغل/امکانات پلتفرم
> Job)، `sso.pdf` (مشخصات فنی سرویس Auth مرکزی)، `tools.pdf` و `tools2.pdf`
> (دیتاشیت ابزارهای مشترک: Meilisearch، Umami، Uptime Kuma، Adminer).

## ۱) خلاصهٔ مدیریتی — حکم کلی

**حکم کلی:** معماری‌ای که در پنج سند پیشنهاد شده، از نظر مهندسی **جهت درست و امروزی**
است (modular monolith + چندمستأجری با `tenant_id`، هویت مرکزی، و سرور ابزار مشترک).
اما **طرح سخت‌افزاری فعلی برای این معماری کافی نیست** و نقطهٔ اصلی خطر همان‌جاست:

- **۱ هسته + ۳ گیگ برای هر پلتفرم مستقل: روی کاغذ قبول، در واقعیت پرریسک.** خودِ
  آلوشمال در حال حاضر (کاربر کم، ترافیک پایین) حدود **۱٬۰۳۵ مگابایت** RAM مصرف می‌کند؛
  یعنی حتی پیش از بار واقعی، روی یک سرورِ ۳ گیگ حدود ۳۴٪ را گرفته‌ایم — بدون هیچ
  فضایی برای peak.
- **دو پلتفرم را جدا بالا آوردن، خلاف توصیهٔ خودِ سند است.** سند `tools` می‌گوید یک
  سرور ۴ گیگ می‌تواند ۳ تا ۴ پروژه را سرو کند؛ این با «هر پلتفرم یک سرور
  ۱-core/3GB» در تناقض است.
- **مسیر پیشنهادی درست:** پلتفرم‌ها را روی **یک استک Docker Compose مشترک** با
  دیتابیس‌های مجزا و Nginx به‌عنوان reverse proxy واحد بیاوریم؛ و سرور دوم را برای
  ابزارها + بکاپ اختصاص دهیم. این کار هم ارزان‌تر و هم قابل‌نگهداری‌تر است.

## ۲) آنچه از اسناد می‌خوانیم

### ۲.۱ پلتفرم Job (`job1.pdf` + `job2.pdf`)

- **هدف:** SaaS مدیریت کسب‌وکار با «موتور امکانات پویا» — ادمین مشاغل (مربی ورزشی،
  مشاور املاک، …) و امکانات هر شغل را تعریف می‌کند و هر صاحب کسب‌وکار پنلی دقیقاً
  متناسب با شغل خود می‌گیرد.
- **معماری فنی:** NestJS (modular monolith) + Next.js + Prisma + PostgreSQL +
  Nginx + Docker Compose.
- **سه لایه پنل:** ادمین پلتفرم (بالاترین سطح) ← پنل Owner (صاحب کسب‌وکار) ← پنل
  Staff (دسترسی محدود/فقط‌خواندنی).
- **هستهٔ داده:** چندمستأجری با ستون `tenant_id` در جداول مشترک؛ جدول‌های میان‌دار
  مانند `TenantModule`، `BusinessType`، `FeatureType`، `Feature`.
- **مدل ارائه:** Rest/CRUD؛ حدود ۲ گیگ RAM برای کل استک هدف‌گذاری شده است.

### ۲.۲ سرویس هویت مرکزی SSO (`sso.pdf`)

- یک میکروسرویس مستقل NestJS برای احراز هویت مرکزی که **فروشگاه، آگهی‌ها و
  پروژه‌های دیگر** از آن استفاده می‌کنند.
- احراز هویت با **موبایل + OTP** (سازگار با اکوسیستم ایران مانند کاوه‌نگار/ملی‌پیامک)،
  ثبت‌نام/ورود بدون رمز.
- توکن: **JWT + چرخش Refresh Token (Refresh Token Rotation)** با عمر کوتاه access،
  و رمزنگاری `argon2`/`bcrypt` برای توکن‌های ذخیره‌شده.
- جریان OAuth-مانند: «Authorization Ticket» (کد یک‌بارمصرف ۳۰ ثانیه‌ای) و `IdP`
  مرکزی؛ جداسازی دادهٔ هر پروژه با `client_id` و `allowedRedirectUris`.
- اصل طراحی: «هویت را فقط سرویس مرکزی می‌شناسد؛ داده‌های اختصاصی هر پروژه (سبد
  خرید، آگهی‌ها، فیلدها) در دیتابیس همان پروژه ذخیره می‌شود.»

### ۲.۳ استک ابزارهای مشترک (`tools.pdf` + `tools2.pdf`)

- چهار ابزار: **Meilisearch** (جستجو)، **Umami** (آنالیتیکس)، **Uptime Kuma**
  (مانیتورینگ)، **Adminer** (مدیریت دیتابیس).
- فازبندی پیاده‌سازی و بوت‌استرپ ماژولار: امنیت/کاربران ← مشاغل ← پنل Owner ←
  مشاغل نمونه ← پنل Staff و RBAC.
- الگو: هر ابزار با `tenant_id`؛ «اسکوپ API Key» در Meilisearch برای جلوگیری از
  نفوذ بین پروژه‌ها.
- **ادعای مهم سند:** «۴ ابزار در حد ۴۰۰ تا ۶۵۰ مگابایت RAM» و «یک سرور ۴ گیگ
  می‌تواند ۳ تا ۴ پروژهٔ مستقل را سرو کند.»

## ۳) تحلیل معماری — چه چیزی درست است (نقاط قوت)

| قوت | چرا مهم است |
| --- | --- |
| هویت مرکزی (SSO) درست طراحی شده | جدا کردن «هویت» از «دادهٔ کسب‌وکار هر پروژه» تصمیم بالغی است؛ تکرار لاگین و رمز را حذف و افزودن پروژهٔ جدید را ارزان می‌کند. |
| موتور امکانات پویا (`Feature`/`BusinessType`) | به‌جای کدنویسی برای هر شغل، ترکیب ماژول‌ها از دیتابیس خوانده می‌شود — همان ایدهٔ پلن/سهمیهٔ آلوشمال، اما عمومی‌تر و قوی‌تر. |
| یکتایی `tenant_id` + فیلتر سراسری/RLS | الگوی denormalized `tenant_id` همراه Prisma + RLS همان راه‌حل توصیه‌شدهٔ B2B است؛ مقیاس‌پذیر و نسبتاً ساده. |
| اختیاری‌بودن هر ابزار | «هر ابزار را می‌توان مستقل استفاده کرد» ریسک وابستگی را کم می‌کند و اجازه می‌دهد مرحله‌ای پیش برویم. |
| استک یکدست (TS/NestJS/NextJS) | هزینهٔ نگهداری و استخدام نیرو پایین می‌ماند؛ تیم با یک زبان و یک الگو کار می‌کند. |

## ۴) تحلیل — نقاط ضعف و ریسک‌ها

| ریسک / ضعف | توضیح و اثر |
| --- | --- |
| سرور فعلی کم‌توان برای بار واقعی | ۱ هستهٔ CPU سقف سختی است: یک build Next.js یا یک کوئری سنگین، بقیهٔ سرویس‌ها را قفل می‌کند. ۳ گیگ RAM با آلوشمال (≈۱ گیگ) + ابزارها + دیتابیس جدید، به swap می‌خورد. |
| چندمستأجری Job + هویت مستقل = پیچیدگی زیاد در زمان کم | تا وقتی آلوشمال خودش در حال تکمیل است، شروع همزمان پلتفرم دوم با SSO و ابزارها بار شناختی/عملیاتی زیادی می‌آورد و کیفیت هر دو را پایین می‌آورد. |
| ابزارها بدون «هم‌فهمی امنیتی» خطرناک‌اند | Adminer درگاه ورود به کل پایگاه داده است؛ Umami/Meilisearch هم دادهٔ همهٔ پروژه‌ها را دارند. اگر ایزوله نشوند، یک نفوذ = نفوذ به همه. |
| هزینهٔ پنهان بکاپ/بازیابی | سند به بکاپ اشاره دارد اما در تقسیم سرورها لحاظ نشده؛ بکاپ باید روی سرور/فضای دیگری باشد، وگرنه فاجعهٔ سرور، فاجعهٔ بکاپ هم می‌شود. |
| ریسک «دو سرور = دو بار نگهداری» | Nginx، SSL، Compose، بکاپ و مانیتورینگ باید دو جا تکرار شوند؛ همان دردی که الگوی «سرور مشترک» می‌خواهد حل کند. |
| ابزارها بدون پایهٔ امنیتی/نقش | بدون لاگین مرکزی و RBAC حداقلی، ابزارها به‌سرعت از کنترل خارج می‌شوند. |

## ۵) تحلیل منابع: عدد به عدد

مصرف واقعی استک آلوشمال روی همین سیستم (اندازه‌گیری‌شده با `docker stats` در حالت
بیکاری):

| سرویس | RAM اندازه‌گیری‌شده | نکته |
| --- | --- | --- |
| web (Next.js) | ≈ ۴۶۸ مگابایت | در بار واقعی بیشتر |
| api (NestJS) | ≈ ۴۲۰ مگابایت | |
| db (Postgres) | ≈ ۶۰ مگابایت | الان کوچک؛ با دادهٔ واقعی معمولاً بزرگ‌تر می‌شود |
| minio (Object Storage) | ≈ ۸۱ مگابایت | |
| redis | ≈ ۴ مگابایت | |
| **جمع** | **≈ ۱٬۰۳۵ مگابایت** | فقط آلوشمال، بدون ابزار مشترک |

با این حساب:

- روی سرور **۳ گیگ**: آلوشمال ≈۱ گیگ + ابزارها (Meilisearch/Uptime/Umami/Adminer)
  ≈۵۰۰–۶۵۰ مگ + (اگر Job هم بیاید) ≈۱–۱٫۵ گیگ دیگر = **بالای ۳ گیگ**. نتیجه: OOM یا
  swap شدید.
- روی سرور **۴ گیگ** (ادعای خودِ سند tools): فقط ابزارها + یکی از دو پلتفرم در حالت
  سبک جا می‌شود — نه هر دو سنگین.
- **پس «۱ هسته + ۳ گیگ برای هر پلتفرم جدا» توصیه نمی‌شود.**

## ۶) معماری پیشنهادی (جایگزین «هر پلتفرم یک سرور»)

| سرور | مشخصه | چه چیزی روی آن | چرا |
| --- | --- | --- | --- |
| **سرور A — لبه و سرویس‌ها** | ۲ هسته / ۴ گیگ (حداقل) | Nginx واحد + Compose مشترک: آلوشمال (web/api/db/minio/redis) + Job (web/api/db)؛ دیتابیس مجزا برای هر پروژه | یک نقطهٔ نگهداری، SSL و reverse proxy واحد، هزینهٔ کمتر |
| **سرور B — ابزارها و بکاپ** | ۲ هسته / ۴ گیگ | Meilisearch + Umami + Uptime Kuma + Adminer + اسکریپت بکاپ زمان‌بندی‌شده + Object Storage بکاپ | ایزوله‌سازی ابزارها از سرویس‌های اصلی؛ بکاپ جدا از دیتای اصلی |

**نکتهٔ کلیدی:** SSO هم روی **سرور A** به‌عنوان یک سرویس NestJS مستقل (سبک، ≈۱۵۰ مگ)
بالا بیاید؛ نه اینکه پلتفرم‌ها را از هم جدا کند. این با روح هر پنج سند هم‌راستاست.

### مسیر مرحله‌ای (اگر بودجه محدود است)

1. **فاز ۱ (اکنون):** آلوشمال را روی سرور فعلی نگه دارید. فقط ابزارهای لازم
   (Uptime Kuma + بکاپ) را روی همان سرور بالا بیاورید. Job را شروع نکنید.
2. **فاز ۲:** با رشد ترافیک یا شروع جدی Job، یکی از دو کار: ارتقای سرور فعلی به
   ۲ هسته/۴ گیگ، یا افزودن سرور B برای ابزارها و بکاپ.
3. **فاز ۳:** SSO به‌عنوان سرویس مشترک + اتصال Job و آلوشمال به آن؛ ابزارها با
   اسکوپ API Key.

## ۷) پیش‌نیازهای غیرقابل‌عبور

- **بکاپ روی سرور/فضای جدا:** بکاپ دیتابیس هر پلتفرم + دادهٔ Uptime Kuma + ایندکس
  Meilisearch، به‌صورت زمان‌بندی‌شده و آفلاین/آبجکت‌استوری جدا.
- **ایزوله‌سازی شبکه:** هیچ پورت دیتابیس/Meilisearch/Adminer مستقیماً به اینترنت باز
  نشود؛ فقط از طریق Nginx و IP allowlist / Basic Auth.
- **رمز و کلید:** Master Key هرگز در تنظیمات نباشد؛ هر پروژه API Key اسکوپ‌دار جداگانه.
- **مانیتورینگ از روز اول:** Uptime Kuma + هشدار تلگرام/ایمیل برای داون‌شدن و
  پرشدن دیسک.
- **محدودسازی CPU/RAM کانتینرها:** هر سرویس `mem_limit`/`cpus` داشته باشد تا یک
  سرویس کل سرور را نخورد.

## ۸) جمع‌بندی و توصیهٔ نهایی

1. **اسناد از نظر مهندسی قوی‌اند.** هر سه سند (Job، SSO، ابزارها) معماری مدرن و
   درست را توصیف می‌کنند؛ مشکل در **برنامهٔ اجرا و زیرساخت** است، نه در طراحی.
2. **«۱ هسته / ۳ گیگ برای هر پلتفرم جدا» را اجرا نکنید.** با اندازه‌گیری واقعی، این
   مقدار برای یک پلتفرم با ابزارهای مشترک کافی نیست، و برای دو پلتفرم قطعاً نه.
3. **توصیه:** یک سرور ۲-core/4GB واحد برای پلتفرم‌ها (Compose مشترک، دیتابیس‌های
   مجزا) + یک سرور ۲-core/4GB برای ابزارها و بکاپ. اگر فعلاً بودجه نیست، همان یک
   سرور را ارتقا دهید و Job را به فاز بعد موکول کنید.
4. **ترتیب درست کار:** اول آلوشمال را پایدار کنید → بعد SSO را بسازید → بعد Job را
   روی SSO سوار کنید → ابزارها را آخر اضافه کنید. نه همه با هم.

> این سند صرفاً تحلیل کارشناسی بر پایهٔ اسناد و اندازه‌گیری‌های لحظه‌ای است و تعهد
> اجرایی ایجاد نمی‌کند.
